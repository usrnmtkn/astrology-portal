# Codex handoff: transits to natal + synastry (v1)

## Split of responsibilities

The package supplies COPY. The app engine supplies SELECTION. Codex implements selection per `TLDR-Daily-Transit-Baseline-Spec.md`; the package renders whatever the engine picks.

### Selection logic (engine side, from the owner's spec)

1. **Headline driver: the transiting Moon.** Its sign, whole-sign house in the reader's chart, and applying aspects pick the day's headline card. Never headline with a slow transit; the Moon is why dailies change daily.
2. **Areas of your life:** one section per qualifying non-Moon transit, ordered by orb tightness. Orb gates: outers + Saturn qualify at <= 3 degrees, inners at <= 5 degrees. Wider transits do not appear that day.
3. **Headliner days:** any Saturn-through-Pluto transit at orb <= 1.0 degree, any station on a natal point, or any return upgrades the day and earns the bespoke deep section. Never generate a bespoke deep section for a sub-threshold transit.
4. Every daily card needs its derivation record (driving transit + orb + application, house of contact, rulership condition, source grounding) per spec section 8.

### Rendering (package side)

- `renderTransitAspect({ transiting, natal, aspect, variant, window })`
  - Authored cards render first (mirror rule, heavy-aware conjunction sharing); fallback template otherwise; SOURCE_GAP only for out-of-package bodies.
  - `window` override: pass an exact phrase ("For the next ten days") when the engine knows the real window; otherwise speed-based defaults apply (Moon = "Today", Sun/Mercury/Venus = "This week", Mars = "For the next couple of weeks", Jupiter = "This month", slow bodies = "For the next few months").
  - Covers all 13 transiting bodies x 16 natal targets (13 bodies + 4 angles) x 5 aspects: verified 1,040/1,040 render.
- Fallback variant rotation: the 26 transit effect lines each have 2 variants (`.../variant-2`, `.../variant-3`). Pass `variant: 2` or `variant: 3` to `renderTransitAspect` to rotate wording for repeat viewers (suggested: stable per user+transit, e.g. `(userId + transitId) % 3`, so a reader sees consistent copy within one transit but fresh copy across transits). No variant param = base line.
- `renderTransitHouse({ planet, house, window })` — 156/156 render; per-planet house-effect lines say what the planet does to that area.
- `renderSynastryAspect({ planetA, planetB, aspect, otherName })` — planetA is the reader's. Returns `headline` (astrology), `tag` (plain-English quality chip: Easy Understanding / Easy Opening / Productive Friction / Balancing Act / Amplified), `body`. Direction matters; do not swap A/B to reuse a render.
- `renderTransitRetro({ planet, sign, window })` — retrograde season card (checks `authored/transit-retro/{planet}` first). Covers the nine bodies that retrograde: Mercury through Pluto plus Chiron. Sun/Moon never retrograde and the nodes almost always are, so those are SOURCE_GAP by design. Default windows use typical retrograde lengths; always pass real dates ("Until August 11") when known.
- `renderTransitAspect` also accepts `isRetrograde: true` — the fallback render appends the repeat-pass line ("this contact usually repeats... revise, not redo"). Authored cards stay verbatim; show retro context via `renderTransitRetro` alongside if needed.
- `renderCompat` — unchanged; refuses reversed directional pair cards by design.
- `renderTransitLabel({ transiting, natal, aspect, window })` — one-line labels for the daily "behind this forecast" stack (Co-Star pattern): `{Planet} {transforming|challenging|boosting} {life area}` plus a duration string. Verb map: conjunction = transforming, hard = challenging, soft = boosting ("facilitating" is banned vocabulary). Pass `window` with the real ephemeris phrase ("Through Saturday", "Two weeks"); order the list soonest-ending first. Tapping an entry opens the full `renderTransitAspect` page.

- `renderBondTransit({ transiting, aspect, planetA, planetB, natalAspect, otherName, sign, window })` — "transits to your bond": a transiting planet activating a synastry contact between the reader and a friend. `planetA` is always the reader's planet, `planetB` the friend's, `natalAspect` the synastry aspect between them (colors the bond-quality line). Selection (engine): only contacts already surfaced on the pair's synastry page qualify; gate the transit at <= 1 degree to either endpoint of the contact (tighter than natal transits, because two charts are involved); pass the real `window`. Renders reader-perspective; produce the friend's mirrored card by calling again with roles swapped, never by editing output. Surfaces: friend profile ("between you two right now"), circle feed (reader-inclusive tier-2 story when active), notifications. 260 combos verified, parity 195/195.
- `renderSkyAspectCard({ a, b, aspect, aSign, bSign, dateLine })` — the Gifts/Lessons cards on sky placement pages. Collective voice, slower-planet-acts logic, 390/390 combos verified. Sky pages must never serve `renderTransitAspect` output (that is natal-chart copy for the You page).
- `renderCircleStory({ trigger, names, includesReader, members, ... })` — Friends Circle feed group cards; full API and product logic in `FRIENDS-CIRCLE-FEED-SPEC.md`. Also exports `formatCircleNames`.
- `renderSkyLunation` upgrades: accepts `kind: "eclipse-solar" | "eclipse-lunar"` (eclipse opener/close canon, NO intention/ritual sections on eclipses), `northSign`/`southSign` (nodal axis paragraph), and `variant` (e.g. `"year-end"` for the NYE Capricorn New Moon). The per-sign section now renders the owner's authored cards first (all 12 NM + 12 FM ingested, with Set-your-intention / Ritual / closing-question paragraphs appended on regular lunations). Headline becomes "Solar/Lunar Eclipse in {Sign}" for eclipse kinds. See `OWNER-LUNATION-TEMPLATE-LIBRARY.md`.
- `renderSkyPlacement({ planet, sign, events })` — sky page planet-in-sign article (the page the legacy "active in a bold, fast, self-starting way... treat it as weather" helper was serving; decommission that path). Title + duration are app chrome; this returns the longer-form write-up: per-planet pace/theme paragraph in the sign's register, sign lore, the sign's trap, then one paragraph per engine-supplied aspect event (same event objects as `renderSkySeason`; pass sentence-initial dateLines like "Through Saturday"). Covers all 13 bodies x 12 signs (156/156, parity-verified). Article structure follows the owner's ingress-sample register: you-voice opener, mechanics/collective write-up, sign lore, sign trap, practice, aspect paragraphs across the duration, element collective close, blessing sign-off. Owner-authored ingress articles at `authored/sky-ingress/{planet}/{sign}` render verbatim first. The aspect list under the article ("Gifts"/"Lessons" cards) must also stop rendering glossary text ("~2 Signs / ~60°...") and use these event frames or `renderTransitLabel`.
