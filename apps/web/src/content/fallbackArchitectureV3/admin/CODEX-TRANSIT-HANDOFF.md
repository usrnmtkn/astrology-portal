# Codex handoff: transits to natal + synastry (v1)

## Split of responsibilities

The package supplies COPY. The app engine supplies SELECTION. Codex implements selection per `TLDR-Daily-Transit-Baseline-Spec.md`; the package renders whatever the engine picks.

### Selection logic (engine side, from the owner's spec)

1. **Headline driver: the transiting Moon.** Its sign, whole-sign house in the reader's chart, and applying aspects pick the day's headline card. Never headline with a slow transit; the Moon is why dailies change daily.
2. **Areas of your life:** one section per qualifying non-Moon transit, ordered by orb tightness. Orb gates: outers + Saturn qualify at <= 3 degrees, inners at <= 5 degrees. Wider transits do not appear that day.
3. **Headliner days:** any Saturn-through-Pluto transit at orb <= 1.0 degree, any station on a natal point, or any return upgrades the day and earns the bespoke deep section. Never generate a bespoke deep section for a sub-threshold transit.
4. **Beat dedupe:** some authored cards share a rhetorical beat (e.g. the North Node "stop calling it coincidence" card and the Mercury retrograde "none of it is random" card). Do not surface two same-beat cards on one day; the affected cards carry the pairing in their `editorial_notes` field (moved there from the bodies in the 2026-07-22 cleanup — `editorial_notes` is authoring/engine metadata and NEVER renders).
5. Every daily card needs its derivation record (driving transit + orb + application, house of contact, rulership condition, source grounding) per spec section 8.

### Rendering (package side)

- `renderTransitAspect({ transiting, natal, aspect, variant, window, voice })` — pass `voice: friendName` on friend charts: renders authored friend-voice fallback only (the reader-voice authored library never appears in friend view; variants are reader-only). Same for `renderTransitHouse`. Friend retro/return seasons: use `renderTransitLabel` one-liners, not full cards.
  - Authored cards render first (mirror rule, heavy-aware conjunction sharing); fallback template otherwise; SOURCE_GAP only for out-of-package bodies.
  - `window` override: pass an exact phrase ("For the next ten days") when the engine knows the real window; otherwise speed-based defaults apply (Moon = "Today", Sun/Mercury/Venus = "This week", Mars = "For the next couple of weeks", Jupiter = "This month", slow bodies = "For the next few months").
  - Covers all 13 transiting bodies x 16 natal targets (13 bodies + 4 angles) x 5 aspects: verified 1,040/1,040 render.
- Fallback variant rotation: the 26 transit effect lines each have 2 variants (`.../variant-2`, `.../variant-3`). Pass `variant: 2` or `variant: 3` to `renderTransitAspect` to rotate wording for repeat viewers (suggested: stable per user+transit, e.g. `(userId + transitId) % 3`, so a reader sees consistent copy within one transit but fresh copy across transits). No variant param = base line.
- `renderTransitHouse({ planet, house, window })` — 156/156 render; per-planet house-effect lines say what the planet does to that area.
- `renderSynastryAspect({ planetA, planetB, aspect, otherName })` — the CONNECTIONS page (owner naming: the between-two-charts surface is called "Connections" in the app, not "Bonds"). planetA is the reader's. Returns `headline` (astrology), `tag` (plain-English quality chip: Easy Understanding / Easy Opening / Productive Friction / Balancing Act / Amplified), `body`. Direction matters; do not swap A/B to reuse a render.
- `renderTransitRetro({ planet, sign, window })` — retrograde season card (checks `authored/transit-retro/{planet}` first). Covers the nine bodies that retrograde: Mercury through Pluto plus Chiron. Sun/Moon never retrograde and the nodes almost always are, so those are SOURCE_GAP by design. Default windows use typical retrograde lengths; always pass real dates ("Until August 11") when known.
- `renderTransitAspect` also accepts `isRetrograde: true` — the fallback render appends the repeat-pass line ("this contact usually repeats... revise, not redo"). Authored cards stay verbatim; show retro context via `renderTransitRetro` alongside if needed.
- `renderCompat` — unchanged; refuses reversed directional pair cards by design.
- `renderTransitLabel({ transiting, natal, aspect, window })` — one-line labels for the daily "behind this forecast" stack (Co-Star pattern): `{Planet} {transforming|challenging|boosting} {life area}` plus a duration string. Verb map: conjunction = transforming, hard = challenging, soft = boosting ("facilitating" is banned vocabulary). Pass `window` with the real ephemeris phrase ("Through Saturday", "Two weeks"); order the list soonest-ending first. Tapping an entry opens the full `renderTransitAspect` page.

- `renderBondTransit({ transiting, aspect, planetA, planetB, natalAspect, otherName, sign, variant, window })` — `variant: 2` or `3` rotates the effect line for repeat viewers (same rotation rule as natal transit cards: stable per user+transit). Friend-voice `renderTransitAspect`/`renderTransitHouse` calls now also accept `variant` (the variant rows carry they-voice bodies). — connection transits (Connections page; function name kept for API stability): a transiting planet activating a synastry contact between the reader and a friend. `planetA` is always the reader's planet, `planetB` the friend's, `natalAspect` the synastry aspect between them (colors the bond-quality line). Selection (engine): only contacts already surfaced on the pair's synastry page qualify; gate the transit at <= 1 degree to either endpoint of the contact (tighter than natal transits, because two charts are involved); pass the real `window`. Renders reader-perspective; produce the friend's mirrored card by calling again with roles swapped, never by editing output.
